● Let me walk through the whole pipeline — what Netdata actually does with
  cgroups — and then re-trace the failure chain through it.

  What a cgroup is, to Netdata

  Every container, pod, and systemd service on a Linux box gets a directory
  under /sys/fs/cgroup/... where the kernel accounts its CPU, memory, and I/O.
  On a k8s node a pod container looks like:

  /sys/fs/cgroup/kubepods.slice/kubepods-burstable-pod3f1a2b….slice/cri-containe
  rd-9c2e4d….scope

  That path is the cgroup's id — machine-generated, unique per pod instance, and
  meaningless to humans.

  The cgroups.plugin pipeline (inside the netdata daemon)

  It's an internal C plugin with a discovery thread (CGDISCOVER, in
  src/collectors/cgroups.plugin/cgroup-discovery.c) that runs every ~10s:

  1. Walk /sys/fs/cgroup and find all cgroup directories (path-level
  include/exclude patterns decide where it even looks).
  2. Rename each newly found cgroup: raw id → friendly name. This is done by
  spawning an external helper program once per new cgroup
  (cgroup-discovery.c:196-276). The helper looks up who the cgroup belongs to:
    - k8s ids (kubepods…): query the Kubernetes API server (or kubelet) for the
  node's pod list, map container-id → k8s_<namespace>_<podname>_<container> plus
  k8s labels. Because pod metadata may lag pod startup, k8s renames are retried
  up to 9 times (cgroup-discovery.c:1008).
    - docker ids (docker-<64hex>.scope): ask the docker socket for the container
  name.
    - If nothing resolves, the cgroup keeps its raw id as its name.
  3. Filter: decide whether to monitor this cgroup, using pattern lists from
  netdata.conf. The one staging overrides is name-based:
  [plugin:cgroups]
  enable by default cgroups names matching = !*cronjob* *
  3. i.e. "monitor everything, except anything whose name contains cronjob".
  This match runs against the resolved name.
  4. Create charts for each accepted cgroup: ~25 charts / ~50 dimensions (cpu,
  memory, io, pids, network…).
  5. Obsolete the charts when the cgroup disappears (pod exits). Obsolete charts
  are not freed immediately — they linger for cleanup obsolete charts after =
  3600s by default (src/daemon/config/netdata-conf-db.c:14), holding their
  memory the whole hour.

  Two more facts that set the stage:

  - In mode = ram (staging children), every dimension owns a ring buffer of
  retention × 4 bytes = 28.8KB at retention 7200 (src/database/rrddim.c:81). So
  one pod ≈ 25 charts ≈ 50 dims ≈ ~1.5MB of ring memory + metadata, held until
  an hour after the pod dies.
  - Staging children have a 512Mi hard limit and, at their normal dimension
  count, idle at roughly 450-500MB. There is almost no headroom.

  Why the cronjob exclusion exists at all

  CronJob pods are the pathological case for this pipeline: a new pod (= new
  cgroup = new chart set) every minute, dead 30 seconds later. Without the
  exclusion, a child accumulates a rolling window of dead-pod charts: at one
  cronjob-pod per minute, that's ~60 lingering chart-sets × ~1.5MB ≈ ~90MB of 
  permanently-wasted memory per churny workload — and staging has multiple
  cronjobs. Someone was burned by this before; that's why the filter is in the
  config.

  What changed on Jul 13, and how the chain breaks

  Commit 70c9e64076 replaced the rename helper — a 741-line shell script
  (cgroup-name.sh) that shipped with every install — with a compiled Go binary
  (cgroup-name) built and installed separately.

  The chain of consequences when that helper is missing or failing:

  1. Helper unavailable → the plugin logs cgroup renaming is disabled and stops 
  resolving names entirely (verified in my rig — this is a real branch, not a
  theory).
  2. Every cgroup's "name" stays its raw id: kubepods-…pod<uid>…. No raw id
  contains the string cronjob.
  3. Therefore !*cronjob* matches nothing → cronjob pods get monitored again,
  and every name-based filter in the config silently becomes a no-op. In my rig,
  broken renaming also widened the monitored set (extra sub-cgroups got charts
  that the named run never created) — so it's "more cgroups" on top of "wrong
  cgroups".
  4. Each churned pod now costs ~1.5MB for an hour after death. Plus, raw
  pod-UID names are unique per pod instance, so nothing is ever reused — every
  pod cycle is a fresh chart set.
  5. The child was already at ~450-500MB of 512Mi. The churn tail adds
  tens-to-hundreds of MB depending on the node's pod turnover → the kernel
  OOM-kills the container.

  Why the new helper can fail where the shell couldn't:

  - Existence: the shell script was part of the base install; the Go binary is a
  separate build artifact — a packaging gap in any image variant means it's
  simply not there (that's the exact branch my dev build hit).
  - TLS: the old shell fetched pod metadata with curl -sSk — the -k means it
  never verified TLS. The Go helper verifies the API server's certificate
  against the mounted service-account CA and fails closed if that doesn't check
  out. And the API-server path is the default one — the helm chart's useKubelet
  option defaults to false.
  - It's young code: it already needed one production hotfix four days after
  merge (ef3949dce3, a timeout-environment race).

  - Verified locally: the "helper missing → renaming disabled → raw names + more
  cgroups monitored" branch, the 28.8KB/dim ring math, the 3600s obsolete
  linger, and that a working HEAD behaves identically to the pre-change build

  - Still hypothesis: that this is what's happening on staging's children. I

● Final root-cause report — children OOMs

  TL;DR: Reproduced and root-caused. Three stacked defects: (1) since Apr 2025,
  charts obsoleted at chart level are never freed — this is the leak; (2) since
  Jul 7, ram-engine metric handles are born with refcount 2, so even
  correctly-freed dimensions leak their ring buffers; (3) the Jul 13 cgroup-name
  helper replacement is the likely trigger that turned latent leaks into daily
  OOMs by unleashing cronjob-pod churn. All three are proven on the local rig
  with instrumented builds; only the staging-side trigger confirmation remains.

  Defect 1 — chart-level obsoletion never frees (the staging child leak)

  - svc_rrddim_obsolete_to_archive (src/daemon/service.c:8) refuses to archive a
  dimension unless it carries RRDDIM_FLAG_OBSOLETE. Chart-level obsoletion —
  used by cgroups.plugin (cgroup-discovery.c:47-83), go.d job stops, plugin
  exits, and child-disconnect mass obsoletion — never sets dimension flags
  (pluginsd_parser.c:542 sets them only for per-DIMENSION "obsolete").
  - So every cleanup pass counts candidates it can't archive, re-arms
  OBSOLETE_DIMENSIONS, and rrdset_free() is unreachable. Proven: zero free chart
  worker events under chart-level churn on all four builds
  (-696/-808/-813/-883); frees appear instantly when dimensions are obsoleted
  explicitly; skip counters show skip_dimflag/skip_refs = 0 once flags are set.
  - Introduced by e46080f64f ("Fix memory leaks and service thread corruption",
  2025-04-24): it made the archive count honest, which unmasked the
  missing-dim-flag hole — before it, miscounting let rrdset_free() run anyway.
  - Cost on a mode=ram child: ~28.8KB/dim ring + structs + labels per churned
  chart, forever. Measured: rrd accounting +1.4MB/min and VmData +1.65MB/min at
  25 churned charts/min, on every build.

  Defect 2 — ram handles born with refcount 2 (nightlies since ~Jul 8)

  - rrddim_metric_get_or_create (src/database/ram/rrddim_mem.c:231): the
  creation body sets refcount=1, then the while((mh = get_by_id(...)) == NULL)
  condition re-runs, finds the new handle, and acquires again → one owner, two
  references. At rrddim_free, the release leaves refcount 1 → ring retained
  forever.
  - Proven by instrumentation: every freed dimension logs "handle survived
  rrddim_free with refcount 1"; the extra acquires resolve to get_or_create
  itself (14,592 = one per dimension created); query acquire/release pairs are
  balanced.
  - From the Jul 7 ownership refactor (9ddc54a5ac, in nightly -738+, so in
  staging's -858 too). Masked in staging by defect 1 (charts never reach the
  free path), but it guarantees the leak persists even after defect 1 is fixed.
  Fix is a one-liner-class change.

  Defect 3 (trigger) — cgroup-name replacement unleashed churn

  - Both leaks need churn to matter. Staging's !*cronjob* * filter kept cronjob
